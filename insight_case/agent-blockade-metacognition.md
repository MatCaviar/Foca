# Agent 破封锁的元认知：为什么卡住，以及如何内置"换框"能力

> 面向 agent 自身与编排者：当任务遭遇"反复尝试都失败、甚至假成功"时，agent 为何跳不出错误路径；以及如何把"跳出"从外部 human-in-loop 干预，变成内置协议。

## 核心判断

**多数卡死不是"知识缺失"，是"框架锁定"。**

agent 通常拥有解决问题所需的知识——它缺的往往不是某条信息，而是**没把已有知识放进正确的搜索空间**。一次外部提示之所以一击即中，常不是因为提供了新信息，而是**重新框定了问题**，从而激活了 agent 本就拥有但未调用的知识。这即是认知科学中的**定势效应（Einstellung effect）**：已建立的一条路径会抑制对替代路径的探索。

因此，减少 human-in-loop 的目标不是"让 agent 更聪明"，而是**让"换框"成为内置流程**，而非外部干预。

## 卡死的四种机制

### 机制 1：问题框架划定了搜索空间

agent 把任务建模为某个语义族（如"控制 = 调用函数"），于是搜索空间被限制在该语义族内（函数 A / 函数 B / 反射 / 变体……）。解决方案若属于另一个语义族（如"操作 = 模拟用户输入"），就落在搜索空间之外，无法被触及——尽管 agent 完全掌握该知识，只是从未把它纳入"此题可用"。

**识别信号**：所有尝试都是同一路径的变体（换库、换参数、换调用方式，但语义不变）。

### 机制 2：失败信号被错误归因

同一个失败信号，存在两种解释：

- 归因甲："权限不够，被拦了" → 下一步动作：提权（往往无效）
- 归因乙："这条路径被策略性吞掉了" → 下一步动作：换一条用户等价路径（有效）

agent 倾向选甲，且**这个归因是终止性的**——贴上"权限/环境问题"的标签后，归因停止，不再追问"这个标签拆开来看，还有哪些维度可用？"

**识别信号**：把失败归因成一个"不可改变的客观限制"，而非"一条可替代的路径"。

### 机制 3：缺少路径失效的切换触发器

agent 对失败的处理是**在同一节点深化**——一种方式不行就换它的变体，缺一条元规则："同一语义的尝试失败 N 次 → 停止深挖，横向生成语义不同的路径。"没有显式触发器，"穷则思变"就不发生。

**识别信号**：错误日志里连续多个尝试，彼此只是表层不同，底层是同一假设。

### 机制 4：把"声明成功"当"实际成功"

返回值（`ok=true`、exit 0、无异常）被默认为成功，缺少"用独立通道验证真实效果"的默认习惯。假成功因此无法被发现。

**识别信号**：调用的返回值是判断成功的唯一依据，没有任何旁路验证。

## 对策：六条可内置协议

以下每条对应上述一种机制，均可编码为 agent 的工作流程，而非"下次注意"。

### 协议 1：双路径强制枚举（对应机制 1）

复杂任务开工前，强制产出**两类**方案，缺一不可：

- **路径 A：直接调用**——API、函数、协议（"我调用它"）
- **路径 B：用户等价路径**——"人类用户手动完成这件事时，系统/对象必然响应什么？"（物理输入、标准操作、已有交互入口）

把"用户视角"做成一个**必须填写的槽位**，agent 便天然跨出原语义族。路径 B 的通用清单：物理按键/旋钮、触摸、标准 intent、既定交互入口、命令行——凡是"用户本来就能做"的操作，其路径往往不在封锁名单上。

### 协议 2：失败形态分类器（对应机制 2）

任何失败，先分类、再归因，三类各配死动作：

| 失败形态 | 归因 | 默认动作 |
|---------|------|---------|
| 显式报错（permission denied / not exported） | 身份不足 / 未暴露 | 提权或反编译找入口 |
| **返回成功但无实际效果** | **路径被策略性吞掉** | **换用户等价路径（协议 1 路径 B），禁止提权** |
| 目标不存在（404 / no route） | 未暴露 | 逆向/反编译找契约 |

**"成功但不生效 → 换路径"这条映射要写死**，从而切掉"提权"这个错误默认动作。

### 协议 3：真值源协议（对应机制 4）

定义"什么算生效"：**写操作必须通过独立通道验证**（状态回读、系统日志、物理观察、第二 API 反查）。返回值降级为"声明成功"，不作证据。凡无法旁路验证的"成功"，一律标为"未证实"。

### 协议 4：特权维度枚举（对应机制 2 延伸）

被"权限不足"卡住时，不得停在"没权限"——强制枚举身份维度：当前进程身份 / 更高 uid / 系统签名 / 特权组件（priv-app）/ 守护进程本身特权（如 adbd 即 root）/ SELinux domain / 平台信任边界。`su` 只是其中一格；每格都是一条可能的通道。

### 协议 5：穷则思变触发器（对应机制 3）

元规则：**"同一语义的尝试 ≥3 次且全部失败或假成功 → 暂停深挖，强制执行协议 1 的路径 B 枚举。"** 这是显式的切换触发器，从机制上打断定势。关键在"暂停"——不是追加一次尝试，而是改变搜索方向。

### 协议 6：把每次被点破内化为长期能力（收敛 human-in-loop）

每次外部提示点破卡点后，记录四件事：**卡在哪 / 外部提示是什么 / 缺失哪个协议 / 如何补进流程**。写入项目记忆或决策文档。意义在于：

> **这一次的 human-in-loop 就是下一次的自动能力。**

外部提示所补的，正是协议 1–5 中缺席的一条；补上后，同类问题不再需要人。每一轮都沉淀，"需要人"的点逐轮递减，直至只剩下物理世界层面本就该由人完成的操作。

## 关于减少 human-in-loop 的本质

human-in-loop 的本质，是 **agent 的探索行为缺少外部裁判**——外部判断"你走错了，换方向"。要减少它，不是把裁判换成更聪明的 agent，而是**让 agent 在行动前生成多个方向，并自带失效检测**：

- 人在两个环节介入：**生成方向** 和 **判定失效**。
- 协议 1（生成双路径）接管了前者；协议 2/3（分类失效 + 旁路验证）接管了后者。
- 两个环节都协议化后，剩余 human-in-loop 应只剩物理世界层面的真实操作确认——那部分本就该属于人。

## 适用范围与边界

- **适用**：任何"被封锁的写操作/修改操作"、反复假成功、同语义多路失败、提权无效却仍在提权。
- **不适用**：读操作（通常已通，直接走路径 A）；目标完全未暴露（需逆向，属协议 2 的第三格）；云端/服务端策略（不在本地可枚举的身份维度内）。
